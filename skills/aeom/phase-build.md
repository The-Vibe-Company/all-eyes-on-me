# /aeom: a front from scratch

Part of the `/aeom` skill: [SKILL.md](SKILL.md) says when to read this file (`/aeom build --from-scratch`). From SKILL.md it needs section 0 (the run, its branch), **The result page, served**, **The standard of the front** and **A run that stops, and is taken up again**; from the other files, the product sheet ([product.md](product.md)), the journey files ([journeys.md](journeys.md)), the directions in mockups (section 2d, [phase-mockups.md](phase-mockups.md)) and **Where workers work** and **Briefing any worker** ([phase-wave.md](phase-wave.md)).

## 2e. A front from scratch (`/aeom build --from-scratch <spec file | "a sentence"> [--api <url>]`, or `/aeom build --api <url>`)

For a product with no front yet. AEOM drafts the product sheet and its key journeys from the source, draws three directions and the person picks one, builds the kit and the screens of the key journeys on fake data named as such, measures them, writes the standard, and opens a pull request. Front only: no back end, no business logic, and no server call but those of the API given. A project that already has screens is not one, unless a run built them from scratch and `--api` plugs them in: say so, point to `/aeom`, and stop.

**The API.** With `--api <url>`, the screens read their data from that API instead of the fake module, wherever it provides them. It runs on this machine, on its own fake data: `localhost`, `127.0.0.1`, a `.localhost` or `.test` name; any other address is refused, since AEOM touches no real data. It answers before the run goes on (`curl -s -o /dev/null -w '%{http_code}' <url>`); when it does not, say so and stop. Read its routes from its specification when there is one, an OpenAPI file given or found in the project, otherwise from its code or its answers.

1. **The run and where the front goes.** Section 0: a git repository with a clean tree (the source file the user just wrote is the one change it may hold: copy it, commit nothing of it), `RUN`, the run branch now, its base noted. A repository with no commit yet has no base: say so, ask the user for a first commit, and stop. Note `MAIN="$(git rev-parse --show-toplevel)"` and `BASE=$(git rev-parse HEAD)`, and mark the run with them. The front goes in `front/`, in plain HTML, CSS and JavaScript modules with no build step, which any stack can take over later; building in a framework the project already holds comes later, so say it in one line when there is one:
   - the pages, `front/index.html` and one `front/<screen>.html` per screen;
   - the kit, `front/kit/kit.css` (every colour, type size, space and radius as a custom property, and the classes of the components) and `front/kit/header.js` (the header every page shares, a custom element that renders a sticky `<header>`);
   - the data, read by the pages only through `front/data.js`, which returns what `front/fake/data.js` holds: fake data, named as such at its top, in one module, ready to be replaced by an API;
   - `front/data.md`: each piece of data, the screens that show it, and where it comes from, an API route or the fake module.
2. **The product sheet and its journeys, from the source.** Keep the source in `.aeom/runs/$RUN/source.md` (the file given, or the sentence). Draft the sheet as [product.md](product.md) says, with the source as `(seen: <the spec's file>)`, or `(seen: the prompt)`, and `(to confirm)` for what it does not say; write it with `aeom product`. A spec comes first: what its requirements make a principle or a check fail goes in the sheet's « Accepted exceptions », citing its article, and the directions keep what it fixes, as a charter. Its key journeys, three to five, are written on the screens to build, by their future routes (`/`, `/voies.html`). Write each as `.aeom/journeys/<slug>.json` ([journeys.md](journeys.md)), naming each target by the role and the label the screen will carry: these files are the contract the screens are built to. Then the widths, as section 2c step 5 says (`aeom product --widths`, the question when the sheet only guesses). List the screens: every route the journeys cross.
3. **No cost said.** Nothing is said of what the run costs and nothing waits for a go: the run goes on.
4. **The directions.** When `aeom direction show` exits 0, a direction is kept: say which and from what source; when that source is not the one given, ask whether to build on it or draw new ones. Built on, record it in the run, `aeom direction use --run .aeom/runs/$RUN`, and give the kit brief below `$MAIN/.aeom/direction/` as the direction chosen: no directions drawn. New ones: `aeom direction drop`, then section 2d, steps 3 to 7, with the product sheet as the brief and two screens of the journeys, the first a user lands on and the densest. With `.veebee/style.md`, the directions keep what the charter fixes; without it, they are drawn from the product's world (directions.md). The person picks one; with `--autonome`, the knockout of section 2b, step 7, picks, and when the screening leaves none, three new angles are drawn once; still none, say why and stop.
5. **The kit**: one `aeom-worker`, as **Briefing any worker** says, with the kit brief below. Merge it, commit `.aeom/journeys` with it, and note `KIT_BASE=$(git rev-parse HEAD)`.
6. **The screens**: one `aeom-worker` agent per screen, at once, each in its own worktree from `$KIT_BASE`, with the screen brief below. Before merging one, `git diff --name-only $KIT_BASE <its branch>` lists its page alone: a worker that changed the kit, the data module or another page goes back. Data its screen needs that the fake module lacks, it names in its reply: add it to `front/fake/data.js` and `front/data.js` yourself, then merge. Merge each one as it comes back with its own check passing (`aeom check --dir front --pages <its route> --widths "$WIDTHS" --product .aeom/product.md`).
7. **Measure**, the front served by AEOM itself, every route of the journeys named, since a screen reached by a button has no link to it:
   - `aeom capture --dir front --pages <the routes> --widths "$WIDTHS"` and `aeom check --dir front --pages <the routes> --widths "$WIDTHS" --product .aeom/product.md`, then the page judge of the `aeom-judge` skill on them, its step 1 being this capture;
   - `aeom journey --dir front --journeys .aeom/journeys --widths "$WIDTHS" --out .aeom/runs/$RUN/journeys-end`, with `--api <url>` when one was given, then the journey judge of the `aeom-judge` skill on that replay, its step 1 being this replay: `aeom judge --journeys --captures .aeom/runs/$RUN/journeys-end --votes .aeom/runs/$RUN/journeys-end/votes --out .aeom/runs/$RUN/journeys-end`;
   - `aeom guard --from-scratch .aeom/runs/$RUN/journeys-end --base $BASE`, with `--api <url>` when one was given: the front calls no server but that API, every journey goes to its end, and no protected file changed. A call the API refuses because of the front's origin (CORS: the `console` findings of `aeom check`) is the back's to allow: say that it must allow this machine's origins while AEOM measures (any `http://127.0.0.1` port, or every origin on its development server), and `http://localhost:8080` to open the front after; never work around it in the front;
   - `aeom snapshot .aeom/runs/$RUN/end`.

   A screen that fails a check or a principle, or that a journey breaks on, goes back once to its worker with what fails; then measure again. What still fails is said, never hidden.
8. **The standard, the page, the PR.** The standard of the front from the kit's files, as **The standard of the front** says, committed on the run branch. `aeom report .aeom/runs/$RUN --serve --open`, served as **The result page, served** says: every screen and journey the run built. Then `aeom pr .aeom/runs/$RUN`: its description says the data are fake, in one module. Tell the user how to open the front: its pages load modules, which a browser refuses from a file, so they are served, `python3 -m http.server 8080 -d front`, then http://localhost:8080. Mark `--phase done`.

**Plugging an existing front into its API**, `/aeom build --api <url>` on a front a run built from scratch (`front/data.js` and `front/fake/data.js` hold its data): the run branch, then one `aeom-worker` with the data brief below, then step 7 and step 8. Before merging it, `git diff --name-only $BASE <its branch>` lists `front/data.js`, `front/fake/data.js` and `front/data.md` alone: the screens do not change.

**Data brief.** Give the worker the API's address and specification, `front/data.js`, `front/fake/data.js`, `front/data.md` and the journey files. Ask it to:

> Plug the front's data module into this API. Each function of `front/data.js` reads from the API what it provides, at one base address written once at the top, exactly the address given, never a specification's `servers`, and returns, as a promise, what the screens already read, in the same shape. A call that fails rejects, so the screen shows its error: never a silent fall back on the fake data. What the API does not provide stays in the fake module, and `front/data.md` says, for each piece of data, the screens that show it and where it comes from now, an API route or the fake module, the ones still missing from the API last. Write no business logic to fill a gap of the API: a missing piece stays fake and is said. Change no screen and no other file. Commit, and reply in ten lines at most, the data still missing from the API named.

**Kit brief.** Give the worker the folder of the direction chosen (`.aeom/runs/$RUN/directions/<slug>/`, or `$MAIN/.aeom/direction/` when it was kept), the front's folder and stack, the product sheet's brief, the screens and the journey files. Ask it to:

> Turn this direction into the kit of the front, and build no screen. The kit holds every colour, type size, space and radius as a custom property, and the components the screens will need: buttons, fields, lists, cards, the empty state and the error, each a class or a component. The header every page shares, with the product's navigation to the screens the journeys cross, is one component. Every piece of data the screens show is read through one module, whose every function returns a promise, even on fake data, so an API replaces it without touching a screen; it reads the API when one is given, at one base address written once, exactly the address given, and otherwise returns the fake data of one other module: believable data in the product's language for every screen of the journeys (names, amounts, dates), never lorem ipsum, its file saying at its top that it is fake and will be replaced by the API; what the API does not provide stays fake, never filled by business logic. Write `data.md`: each piece of data, the screens that show it, where it comes from. The header component renders a `<header>` that sticks when you scroll. Pictures are generated where they serve when the brief says images are on, as **Briefing any worker** says, the direction's own copied into the front and listed with `aeom image --adopt`; otherwise SVG or CSS: a pull request lets through no other image. Keep exactly what the direction's pages decided: colours, type, density, the way the main action is put forward. Commit, and reply in ten lines at most.

**Screen brief.** Give the worker its screen's route and file, who is on it, what they came to do and what must be visible (from the sheet), the journey files that cross it, the kit and the data module. Ask it to:

> Build this screen on the kit: its tokens, its classes and its header only, never a colour, a size or a component of your own. Read its data only through the data module: never a call to a server, never data written in the page. Give every control the role and the label the journey files name, exactly, so the journeys can be replayed on it. Its data comes as a promise: a block it fills keeps its room from the start (a min-height, or a skeleton of the same size), so the page does not move when the data comes. Draw its loading, its empty state and its error, in the product's own words: no sentence about the interface or the demo, no hole to fill, no hollow word. Pictures are generated where they serve when the brief says images are on, as **Briefing any worker** says; otherwise SVG or CSS. Change no file but this screen's page; data it needs that the data module lacks, name it in your reply. It holds at the widths given: nothing scrolls sideways, a label stays on one line, cards keep one shape, text is cut only with an ellipsis, what one taps is big enough. Link the other screens as the journeys go. Commit, check your screen with `aeom check --dir front --pages <your route> --widths <the widths> --product "$MAIN/.aeom/product.md"`, fix what fails, and reply in ten lines at most.

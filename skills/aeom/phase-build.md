# /aeom: a front from scratch

Part of the `/aeom` skill: [SKILL.md](SKILL.md) says when to read this file (`/aeom build --from-scratch`). From SKILL.md it needs section 0 (the run, its branch), **The result page, served**, **The standard of the front** and **A run that stops, and is taken up again**; from the other files, the product sheet ([product.md](product.md)), the journey files ([journeys.md](journeys.md)), the directions from a prompt (section 2d, [phase-prompt.md](phase-prompt.md)) and **Briefing any worker** ([phase-wave.md](phase-wave.md)).

## 2e. A front from scratch (`/aeom build --from-scratch <spec file | "a sentence">`)

For a product with no front yet. AEOM drafts the product sheet and its key journeys from the source, says what the run will cost and waits for the go, draws three directions and the person picks one, builds the kit and the screens of the key journeys on fake data named as such, measures them, writes the standard, and opens a pull request. Front only: no back end, no business logic, no server call. A project that already has screens is not one: say so, point to `/aeom`, and stop.

1. **The run and where the front goes.** Section 0: a git repository with a clean tree, `RUN`, the run branch now, its base noted. When the project has a front stack (a framework in its `package.json`), the front is built in it, in its conventions. Otherwise it goes in `front/`, in plain HTML, CSS and JavaScript modules with no build step, which any stack can take over later:
   - the pages, `front/index.html` and one `front/<screen>.html` per screen;
   - the kit, `front/kit/kit.css` (every colour, type size, space and radius as a custom property, and the classes of the components) and `front/kit/header.js` (the header every page shares, as a custom element);
   - the data, read by the pages only through `front/data.js`, which returns what `front/fake/data.js` holds: fake data, named as such at its top, in one module, ready to be replaced by an API.
2. **The product sheet and its journeys, from the source.** Keep the source in `.aeom/runs/$RUN/source.md` (the file given, or the sentence). Draft the sheet as [product.md](product.md) says, with the source as `(seen: <the spec's file>)`, or `(seen: the prompt)`, and `(to confirm)` for what it does not say; write it with `aeom product`. Its key journeys, three to five, are written on the screens to build, by their future routes (`/`, `/voies.html`). Write each as `.aeom/journeys/<slug>.json` ([journeys.md](journeys.md)), naming each target by the role and the label the screen will carry: these files are the contract the screens are built to. Then the widths, as section 2c step 5 says (`aeom product --widths`, the question when the sheet only guesses). List the screens: every route the journeys cross.
3. **The cost, then wait.** `aeom estimate --from-scratch --screens <how many> --widths "$WIDTHS"`. Show the table, and wait for the go; with `--autonome`, show it and go on.
4. **The directions**: section 2d, steps 3 to 7, with the product sheet as the brief and two screens of the journeys, the first a user lands on and the densest. With `.veebee/style.md`, the directions keep what the charter fixes; without it, they are drawn from the product's world (directions.md). The person picks one; with `--autonome`, the knockout of section 2b, step 7, picks.
5. **The kit**: one worker on Sonnet, as **Briefing any worker** says, with the kit brief below. Merge it, then commit `.aeom/journeys` with it.
6. **The screens**: one worker per screen, at once, each in its own worktree from the run branch after the kit, with the screen brief below. Merge each one as it comes back with its own check passing (`aeom check --dir <front> --pages <its route> --widths "$WIDTHS"`).
7. **Measure**, the front served by AEOM itself:
   - `aeom capture --dir <front> --widths "$WIDTHS"` and `aeom check --dir <front> --widths "$WIDTHS"`, then the page judge of the `aeom-judge` skill on them;
   - `aeom journey --dir <front> --journeys .aeom/journeys --widths "$WIDTHS" --out .aeom/runs/$RUN/journeys-end`, then the journey judge on that replay, `--out .aeom/runs/$RUN/journeys-end`;
   - `aeom guard --from-scratch .aeom/runs/$RUN/journeys-end`: on fake data, the front makes no call;
   - `aeom snapshot .aeom/runs/$RUN/end`.

   A screen that fails a check or a principle, or that a journey breaks on, goes back once to its worker with what fails; then measure again. What still fails is said, never hidden.
8. **The standard, the page, the PR.** The standard of the front from the kit's files, as **The standard of the front** says, committed on the run branch. `aeom report .aeom/runs/$RUN --serve --open`, served as **The result page, served** says: every screen and journey the run built. Then `aeom pr .aeom/runs/$RUN`, whose description says that the data are fake and where they are. Mark `--phase done`.

**Kit brief.** Give the worker the folder of the direction chosen (`.aeom/runs/$RUN/directions/<slug>/`), the front's folder and stack, the product sheet's brief, the screens and the journey files. Ask it to:

> Turn this direction into the kit of the front, and build no screen. The kit holds every colour, type size, space and radius as a custom property, and the components the screens will need: buttons, fields, lists, cards, the empty state and the error, each a class or a component. The header every page shares, with the product's navigation to the screens the journeys cross, is one component. Every piece of data the screens show is read through one module, which returns, today, the fake data of one other module: believable data in the product's language for every screen of the journeys (names, amounts, dates), never lorem ipsum, its file saying at its top that it is fake and will be replaced by the API. Keep exactly what the direction's pages decided: colours, type, density, the way the main action is put forward. Commit, and reply in ten lines at most.

**Screen brief.** Give the worker its screen's route and file, who is on it, what they came to do and what must be visible (from the sheet), the journey files that cross it, the kit and the data module. Ask it to:

> Build this screen on the kit: its tokens, its classes and its header only, never a colour, a size or a component of your own. Read its data only through the data module: never a call to a server, never data written in the page. Give every control the role and the label the journey files name, exactly, so the journeys can be replayed on it. Draw its empty state and its error. It holds at the widths given: nothing scrolls sideways, a label stays on one line, cards keep one shape, text is cut only with an ellipsis, what one taps is big enough. Link the other screens as the journeys go. Commit, check your screen with `aeom check --dir <front> --pages <your route> --widths <the widths>`, fix what fails, and reply in ten lines at most.
